Microservices

MONOLITH 
-> it is similar to a big container wherein all the software components of an application are assembled together and tightly packed

-> all the components will be in a single unit, in one application  will implement all the functionalities 

-> if any feature is not working the complete system goes down, in order to handle this issue, the application needs to re-built, re-tested and also re-deployed

-> it is tightly coupled, changes in one module can affect the other

-> one function or program depends on other

-> Deployed in single bundle

-> Change in one service then whole app is redeployed



SERVICE ORIENTED -> it is essentialy a collection of services. These services communicate with each other. the communication can involve either simple data passing or two or more services coordination some activity

MICROSERVICES 
-> it is an architectural style that stuructures an application as a collection of small autonomous service modeled around a business domain.
 
--> Each micro service is deployed indepentently, have diff port numbers

--> each module is managed independently

--> different teck stack

--> have independent data base for each micro service, one service can use MySQL other can use postgre sql

--> it is fine grained , each service will focus only on single business logic

-->  Fault isolation is easy, even if one service goes down, other can continue to function

--> All microservices should be loosely coupled so that changes made in one does not affect the other, every service should have their respective database


--> no cross dependencies b/w code bases. you can use difference technologies for diff services



MICROSERVICES CHALLENGES

--> Microservice relay on each other and they will have to communicate with each other

--> monitoring the applications - actuators and we should maintain services maintained on different ports

--> Handling microservices is complex

SPRING CLOUD

--> it is a frame work built on the top of spring boot that helps developers build microservices based distributed system easily

1. SERVICE DISCOVERY

- allows services to find each other automatically
- uses Netflix Eureka

2. Centralized Configuration

- stores configuration in one central place
- uses Spring Cloud Config
- updates configs without restarting service
- maintains environment specific configs

3. Load Balancer

- Distributes traffic across multiple service instances
- uses Spring Cloud LoadBalancer
- improves performance

4. Fault Tolerance

- Handles service failures gracefully
- uses Resilience4j
- Circuit breaker, retry, timeout

5. API Gateway

- it acts as a single entry point , every request first goes to the api gateway, api gateway will route to the respective service
- uses Spring Cloud Gateway
- routing, authenticating, looging

6. Distributed Tracing

-Tracks requests across multiple services
- uses Spring Cloud Sleuth
- often integrated with Zipkin

7. Messaging Support

- Enables communication with services
- uses Spring Cloud Stream
- supports Kafka, RabbitMQ

8. Security Support

- Provides secure microservice communication
- Uses OAuth2, JWT, Spring Security

CIRCUID BREAKER

circuit breaker exist in 3 states
- CLOSED 
- OPEN
- HALF OPEN

--> intitally service will be in closed state only

we will be defining the thresholds limits , once the threshold limit crosses the limit then it will move to the open state 

=> management.health.circuitbreaker.enabled= true

=> management.endpoints.web.exposure.include=health

=> resilience4j.circuitbreaker.instance.productserivce.registerHealthIndicator = true

=> resilience4j.circuitbreaker.instance.productserivce.slidingWindowSize=3

=> resilience4j.circuitbreaker.instance.productserivce.minimumNumberOfCalls=3

=> resilience4j.circuitbreaker.instance.productserivce.failuerRateThreshold=50

=> resilience4j.circuitbreaker.instance.productserivce.waitDurationOpenState=10s

=> resilience4j.circuitbreaker.instance.productserivce.permittedNumberOfCallsInHalfOpenState= 2

=> resilience4j.circuitbreaker.instance.productserivce.automaticTransitionFromOpenToHalfOpenEnabled=true


========

slidingWindowSize=5 -> last 5 calls tracked

minimumNumberOfCalls=3 -> start checking after 3 calls

failuerRateThreshold=50 -> if 50% fail => circuit open

waitDurationInOpenState=10s -> wait 10s before retry

permittedNumberOfCallsInHalfOpenState=2 -> Allow 2 test calls

automaticTransitionFromOpenToHalfOpenEnabled=true

for transient failuers we can use retry 

for system or service failuers we can use circuit breaker

circuit breaker states

CLOSED - normal
calls allowed
if failuers exceeds threshold -> move to OPEN

OPEN -  service down
calls blocked
fallback method executed
after wait time -> move to HALF OPEN 

HALF OPEN - testing
limited calls allowed
if success -> CLOSED
if failure -> OPEN
